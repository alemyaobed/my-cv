Render Migration Status & Cost-Benefit Analysis






1. Technical Fixes Complete

The details of the restriction will be covered in detail below.
Efficient Internal Networking: i’ve linked the be-app to botai using an internal URL (http://botai-stag:5000). 
       * Benefit: This traffic is faster, more secure (never leaves Render’s network),
         and saves us a custom domain slot. 
       * our AWS setup only used custom domains for external testing (APIdog), not for internal service-to-service communication, which in fact makes sense.




2. Service Cost Breakdown (Per Environment - stag and prod)
Based on my resource monitoring during testing (botai hit ~960MB RAM / 0.8 CPU peak. For be-app, I couldn't see the metrics because, i needed to be on a plan to be able to see. But everything seemed fine for be-app):
fe-web: $0 (i realized Render provides Static Site hosting for free).
be-app: $7/month (Moving from Free to "Starter" to prevent the app from sleeping/spinning down).
botai: $25/month (Standard tier provides the 2GB RAM / 1 CPU. The current subscription we are on. It seemed okay as i switch to audio2text mode and did some interactions. audio2text since it's the mode that seems to stretch our botai service).
Base Cost: $32/month per environment.




3. Understanding Render’s "Double Billing"
The "Workspace" Billing System. Render has a two-tier pricing model that we need to be aware of. You pay for the Workspace AND the Services (the "servers").


Pipeline Minutes: for each space there is a pipeline minutes, which is the compute time and resource used whenever we run deployments or builds. We get 500 free minutes per month for the whole workspace. We have used 88 minutes so far. With two environments (Stag+ Prod) in a workspace, we will likely exceed 500 minutes. Render charges $5 to add another 1000 minutes. We should budget for at least $5–$10/month here depending on how often we deploy.
The Workspace Plan:
For the workspace, there is a hobby plan, professional plan, organization, etc. but for the sake of this task, we'd be focusing on the hobby and the professional plans


Hobby Plan (Free): 1 project, 2 custom domains, 500 free pipeline minutes


Professional Plan ($19/user/month): Unlimited custom domains, multiple projects, allow up to 10 team members, 500 pipeline minutes/user/month




the current state of things:
we are on the hobby plan and have one workspace, and for that workspace, only 2 services are allowed to have a customized domain name, hence the tradeoffs i did. so it means the two environments i created for that project in the workspaces, i can't get around the custom domain restrictions if we intend to setup prod. so we'd need to either move to the professional plan, or create another workspace dedicated for prod which will also be on the hobby plan


so the benefits and potential total costs:






Option 1: The "Pro Workspace" (Unified):Upgrade the workspace to Professional ($19/user/month).
Pros: Unlimited custom domains; stag and prod live in one project
Cons (The "Minutes" Trap): The workspace fee is $19 per user/month. To get additional pipeline minutes (500 per user), you'd need to add more users — but each additional user costs another $19. This quickly becomes expensive. With just 2 users, that's $38/month for the workspace alone. So with our shared account, paying $19 unlocks custom domains, but you're still limited to 500 minutes. 
The Math: $19 (Workspace) + $25 (botai-stag) + $7 (be-app-stag) + $32 (Prod Services; similar to that of stag) + $10 (pipleline minutes)  = ~$83-$93/month.


Option 2: The "Multi-Hobby" (Cost Saver): Keep the current workspace as stag and create a new, separate Workspace for prod when the time comes.
Pros: Saves $19/month. Each workspace gets its own 2 free domains and its own 500 free build minutes.
Cons: Yet to be verified since we don't have prod set up yet. But i did attempt and it looks plausible. Limited to the 2 custom domains per workspace
The Math: $0 (Workspaces) + $32 (Stag Services) + $32 (Prod Services) + $10 (pipleline minutes) = ~$64-$74/month.




my recommendation:
option 2 would look good if it works, but if we are okay with the cons.

@Alemya Obed Alenyorige Here is what I found about Render deployment failure and service down alerts. 
Render provides two main ways to receive alerts when deployments fail or services become unhealthy. The first method is built-in notifications, where Render sends alerts directly to email or Slack for events such as failed deployments, build failures, or unhealthy services, and it requires no additional setup. The second method is webhooks, where Render sends JSON event data to a webhook endpoint that you control. You can then process and reformat this data and forward it to other platforms such as Google Chat or other messaging systems. In short, built-in notifications are suitable for simple alerting, while webhooks are better for custom integrations.

The first method is built-in notifications, where Render sends alerts directly to email or Slack for events such as failed deployments, build failures, or unhealthy services, and it requires no additional setup. The second method is webhooks, where Render sends JSON event data to a webhook endpoint that you control. You can then process and reformat this data and forward it to other platforms such as Google Chat or other messaging systems. In short, built-in notifications are suitable for simple alerting, while webhooks are better for custom integrations.

That's the conclusion I reached from my findings.

     - This is exactly what I discovered with Amplify... there's no pause button, only delete
